## FOOTPATH НАД ПАРКОВКОЙ — crossing вместо тротуара

### Проблема
Footpath 496695618 пересекает парковку 694466414. Часть тротуара приподнята (корректно), но в середине парковки footpath становится zebra-crossing (некорректно).

### Попытка 16: Parking check at top of `_is_point_on_vehicle_road` (commit 695096d)
**Идея:** Если точка внутри парковочного полигона → return false → footpath остаётся тротуаром.

**Результат:** Частично. Точки ВНУТРИ полигона парковки корректно → off_road. Но через парковку проходит автодорога — точки footpath на ней `on_road=true, in_parking=false` → crossing.

### Попытка 17: Дебаг way_id + детальный вывод
Добавили way_id в пайплайн `_create_road` → thread → `_apply_road_result`.
```
pt=(-83.8,256.8)  on_road=false in_parking=true   ← парковка
pt=(-92.6,255.3)  on_road=false in_parking=false
pt=(-94.7,254.9)  on_road=true  in_parking=false   ← дорога через парковку!
pt=(-96.9,254.5)  on_road=true  in_parking=false
pt=(-110.2,252.2) on_road=true  in_parking=false
pt=(-124.1,249.8) on_road=false in_parking=true    ← опять парковка
```
**Корневая причина:** Автодорога пересекает парковку, полигон парковки не покрывает её.

### Попытка 18: Постобработка "between parking" override
**Идея:** После вычисления `on_road[]` и `in_parking[]`, если `on_road=true` точка между двумя `in_parking=true` участками (±20 точек), → `on_road=false`.

**Дебаг-результат:**
```
OVERRIDE pt 12 → off_road (between parking)
OVERRIDE pt 13 → off_road (between parking)
OVERRIDE pt 14 → off_road (between parking)
```
Парковочный участок: одним непрерывный PATH (23 точки).

**Статус:** Парковочный crossing починен. Z-fighting остался.

### Попытка 19: Z-fighting — bias между чанками
**Идея:** Footway рендерится в двух чанках (-2,0 и -1,0). Bias по Y для одного чанка.
**Результат:** Не помогает (0.001, 0.005, 0.05 — всё без эффекта).

### Попытка 20: Отключение footway 496695618
**Идея:** Полностью пропустить рендер этого footway.
**Результат:** Z-fighting пропадает → подтверждено: z-fighting внутри геометрии footway.

### Попытка 21: Рендер без splitting (один PATH)
**Результат:** Z-fighting остаётся → не из-за splitting, а из-за самих smoothed_points.

### Попытка 22: Удаление zigzag из smoothed_points
**Анализ:** В smoothed_points есть обратный ход:
```
(-133.0,248.2) → (-130.8,248.6) → (-128.7,249.0) — назад!
(-425.5,198.5) — ещё один zigzag
```
Zigzag создаёт перекрывающиеся квады → z-fighting.

**Решение:** Функция `_remove_polyline_zigzag()` — убирает точки с dot(prev_dir, new_dir) < 0.
Результат: 66 → 61 точек (5 zigzag удалено).

**Статус:** Тестируем.

## Known bugs

### Бордюр пропадает на стыке чанков у северного шоссе (~59.150372, 37.949004)
- **Где:** Локальные координаты ~(-20.8, -34.0), chunk -1,-1, граница с chunk 0,-1 или -1,0
- **Что:** Бордюр не виден по краю дороги в том месте, где раньше были треугольники травы
- **Причина:** Шоссе проходит через chunk -1,-1 без узлов — terrain cutout делается spatial hash коридорами (простые прямоугольники из `_road_spatial_hash` сегментов), а не точной геометрией дороги. Прямоугольные коридоры не совпадают с реальным мешем дороги — край террейна (и бордюр) получается не на месте
- **Попытка:** Перенос `_chunk_terrain_roads.erase()` из `_create_deferred_terrain` в `_unload_chunk`, чтобы соседние чанки могли использовать точные коридоры. Не помогло — видимо, проблема не в порядке загрузки, а в том что spatial hash коридоры создают отличающуюся от road geometry геометрию выреза
- **Возможные решения:**
  1. Построить точный коридор из mesh-вершин дороги для сегментов, проходящих через чанк (а не из spatial hash)
  2. Сделать бордюр не по краю terrain cutout, а по реальному краю road mesh (из `_road_spatial_hash` или `smoothed_points`)
  3. Расширить spatial hash коридоры на ~0.3м и добавить бордюр отдельно по центральной линии сегмента
